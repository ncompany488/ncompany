# 피드백 루프 운영 방법

```
 ① critic ──라운드 보고서──▶ ② 총괄 분류(BACKLOG) ──채택 항목──▶ ③ 소유 에이전트 개선
     ▲                                                              │
     └──────── ⑤ 다음 라운드에서 재확인 ◀── ④ reviewer 검증 ◀────────┘
```

## ① 비판 (critic)
- `docs/feedback/rounds/R<번호>-<YYYYMMDD>.md` 에 새 파일로 작성 (기존 파일 수정 금지).
- 먼저 BACKLOG 에서 `완료`/`검증됨` 항목이 실제로 해결됐는지 재확인 → 안 됐으면 `재오픈 요청`.
- 항목마다 **근거(재현 방법·데이터·코드 위치)** 필수. 근거 없는 취향·추측은 쓰지 않는다.

항목 형식:
```
### C-<라운드>-<번호> <한 줄 제목>
- 심각도: P0(서비스 불능·법적 위험) / P1(핵심 기능 결함) / P2(품질·사용성) / P3(아이디어)
- 영역: collector | processor | frontend | alerts | ops | 총괄
- 근거: 재현 절차, 실제 데이터 예시, 파일:줄
- 문제: 무엇이 왜 나쁜가 (사용자 관점 영향)
- 제안: 고치는 방향 (구현 세부는 담당이 결정)
- 완료 기준: 검증 가능한 조건
```

## ② 분류 (총괄)
`BACKLOG.md` 표에 옮기고 상태를 정한다.
- `채택` — 이번 사이클에서 할 것 (P0·P1 우선, 한 사이클 최대 6개)
- `보류` — 가치는 있으나 나중에 (사유)
- `기각` — 근거 부족·규칙 위반·비용 대비 효과 없음 (**사유 필수**, critic 이 다음 라운드에서 반박 가능)

## ③ 개선 (소유 에이전트)
- 채택 항목만, 자기 소유 파일 안에서. 영역 밖 수정이 필요하면 `제안` 으로 보고.
- 비판에 동의하지 않으면 구현 대신 **반론(근거 포함)** 을 보고할 수 있다 → 총괄이 판단.
- 끝나면 `python tools/check.py` 통과 + 무엇을 바꿨는지(파일:줄), 완료 기준 충족 증거.

## ④ 검증 (reviewer)
- 완료 기준을 실제로 재현해 `통과`/`재작업`(이유) 판정. 회귀(다른 기능 깨짐)도 확인.
- 통과 → `검증됨`, 재작업 → 같은 담당에게 1회 재배정 (2회 실패 시 사용자에게 보고).

## ⑤ 재확인 (다음 라운드 critic)
`검증됨` 항목이 실제 사이트/데이터에서도 해결됐는지 확인. 안 됐으면 재오픈.
